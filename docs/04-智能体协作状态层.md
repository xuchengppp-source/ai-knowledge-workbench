# 智能体协作状态层架构

## 1. 定位

解决多智能体（克里斯 / 伊森 / Codex / 卢卡斯）之间"不能通信、任务接力断裂"的问题。

核心立场：智能体之间不需要实时互喊，需要一块公共任务面板——谁做了什么、产出在哪、下一步该谁做，全部可见。接力靠状态流转，不靠对话触发。

参考并复用 `dashi-taskboard`（Codex Taskboard）作为任务面板，不重造轮子。

## 2. 为什么复用 Taskboard

`/Users/xucheng/Documents/Codex项目/dashi-taskboard` 已实现本架构需要的大部分机制：

| 机制 | Taskboard 现状 |
|---|---|
| 任务模型 | 项目 + Issue + 评论，SQLite 本地存储 |
| 状态机 | backlog → todo → in_progress → in_review → done；blocked / canceled |
| 并发防护 | 乐观锁（version + `--if-version`，冲突 exit 5），防止多个智能体抢同一任务 |
| 接力信息 | 评论记录谁做了什么、产出在哪、返工要求 |
| 命令行 | `taskctl` CLI，JSON 输出，任何能执行命令的智能体都可接入 |
| Codex Skill | `manage-taskboard` 已封装完整工作流（搜索 → 认领 → 执行 → 验证 → 评论 → in_review → 用户确认后 done） |
| 云协作 | Cloudflare Worker + D1 + R2 + Basic Auth，支持多设备共用同一面板 |
| Codex 嵌入 | CDP 注入 Codex 侧边栏（launcher / inject 脚本） |

已验证：本机 `node server/index.mjs` 可正常启动，API 监听 `127.0.0.1:47823`，并自动暴露局域网地址。此前"一直没装好"的实际问题是缺少常驻运行与多智能体接入，不是安装失败。

## 3. 分层架构

```text
展示层
  Mac 端  : Taskboard Web UI（127.0.0.1:47823）/ Codex 侧边栏嵌入面板
  手机端  : 工作台「协作」页 / 云端 Taskboard UI（见第 8 节）

接入层（每个智能体一个身份 + 极简 skill，包一层 taskctl）
  Codex  → manage-taskboard skill（原生）
  克里斯 → OpenClaw skill（agent:chris，只允许 create / status / comment）
  伊森   → WorkBuddy skill（agent:ethan，可承担录入 / 整理类任务）
  卢卡斯 → 可选（agent:lucas）

任务事实层
  Taskboard：项目 / 任务 / 评论 / 状态机 / 乐观锁（本地 SQLite，可升级云 D1）

知识关联
  任务产出物通过评论里的 Obsidian 链接关联，Obsidian 仍是最终知识源（只读）
```

## 4. 数据模型与约定

协作项目：建议建一个 `knowledge-pipeline`（知识流水线协作）项目，跨主题任务集中管理；主题密集时可拆子项目。

Issue（任务卡）字段约定：

| 字段 | 约定 |
|---|---|
| title | 一句话任务，如「审核政务招标总结」 |
| description | 背景 + 产出要求 + 验收标准 |
| assignee | `agent:codex` / `agent:chris` / `agent:ethan` / `agent:lucas` / `human:xucheng` |
| status | 沿用 Taskboard 状态机 |
| 产出物 | 评论中放 Obsidian 笔记链接 |
| 归属 | 每次写入通过 `--thread-id` / actor 记录是谁操作 |

## 5. 状态机与接力语义

```text
todo → in_progress   认领（带 --if-version 乐观锁，冲突则跳过，防抢单）
in_progress → in_review  做完 + 自验证 + 评论（产出物 / 结果 / 剩余风险），等审核
in_review → done     审核人确认验收
in_review → in_progress  打回复工（评论写返工要求）
任意状态 → blocked   卡住（评论写卡点）
```

审核人默认 = Codex（符合信任序：Codex 审核 > 混元伊森加工 > M3 克里斯搬运）。伊森承担录入 / 基础整理，克里斯承担微信端便捷录入与搬运，深度梳理与最终审核留在 Codex。

## 5.5 Obsidian 感知层（看板主动识别知识变动）

现状痛点：看板只靠智能体手工推状态，Obsidian 里笔记更新了，任务卡完全不知道，等于"盲板"。

解法：`AI知识学习工作台/scripts/obsidian-watch.mjs` 感知脚本，让看板跟着知识库走。

```text
Obsidian 知识底座（mtime 扫描，最近 N 小时，默认 24h）
  │  白名单目录：AI Agent工程知识 / 企业AI与智能体商业化 /
  │              AI产业链与数字基础设施 / 知识流水线 / Codex工作区
  ▼
任务卡关联（obsidian: 标签 或 描述里的 .md 路径，兼容存量卡）
  ▼
自动动作
  R1 关联笔记变动 → 卡片自动评论「Obsidian 笔记已更新 + 时间」
     → 若卡片是 done → 自动打回 in_review（内容变了需复审）
  R2 --report-card → 更新/创建「[感知] 知识变动日报」卡，列出知识底座变动清单
```

关键点：
- 幂等：每条评论带 `obsidian-watch:<路径>:<mtime>` 标记，重复运行不重复评论（已实测验证）。
- 默认 `dry-run` 只报告，加 `--apply` 才真实写看板；`--report-card` 需配合 `--apply`。
- 用法：`node scripts/obsidian-watch.mjs --window 24 --apply`。
- 触发频率：待常驻化（LaunchAgent / cron 每 15~30 分钟一次），这是全局配置，需徐总确认。

## 5.6 完整接力流程（谁触发 / 谁执行 / 谁看板）

| 环节 | 谁触发 | 谁执行 | 徐总做什么 |
|---|---|---|---|
| 建卡 | 克里斯 / 伊森入库后主动建卡；感知层可自动建卡（开关待定） | 智能体调 `task-card.sh create` | 无需 |
| 发现待审核 | 感知层自动评论 + 看板刷新 | Codex 认领 `in_review` | 打开面板看进度 |
| 审核 | Codex 收到 / 徐总口头指派 | Codex 评论结论，通过置 `done`，有问题打回 | 等结果 |
| 返工 | Codex 打回 `in_progress`（评论写明返工要求） | 克里斯 / 伊森按评论改，改完置 `in_review` | 无需 |
| 笔记再次变动 | 感知层自动发现 | 自动评论 + `done → in_review` | 无需 |
| 完成 | Codex 置 `done` | - | 收尾确认 |

通知档位（解决"智能体不会主动看面板"）：

| 档位 | 机制 | 成本 | 状态 |
|---|---|---|---|
| L0 | 徐总当看板人，手动开 `127.0.0.1:47823` | 零配置 | 当前 |
| L1（推荐） | 常驻脚本轮询面板变化 → 飞书群通知 @伊森/克里斯 | 需飞书 webhook + LaunchAgent | 待确认 |
| L2 | Codex 自动认领审核 | 最省事但烧 DeepSeek 额度，白天高峰期受限 | 暂不建议 |

## 6. 真实接力场景（政务招标案例）

1. 克里斯在微信收到「把政务招标内容总结进 Obsidian」→ 完成入库后，经 OpenClaw skill 建 issue：
   - title：审核政务招标研究
   - status：in_review，assignee：agent:codex
   - 评论：`政务AI Agent工程化与上海6598万招标研究.md`（Obsidian 路径）
2. Codex 看到 in_review 认领 → 审核内容质量与结构 → 评论结果 → 确认无误 `done`，或发现问题打回 in_progress + 返工评论。
3. 若打回，克里斯 / 伊森从评论里的返工要求接着改，改完重新置 in_review。

整个过程徐总无需在多个对话框口头转述，看面板即可知道任务停在哪一步。

## 7. 各智能体接入方式（最小侵入）

- Codex：使用现有 `manage-taskboard` skill，完全能力。
- 克里斯：OpenClaw skill 封装 `taskctl`，仅暴露 3 个动作——建任务、改状态、加评论；参数固定为下拉式（任务标题 / 状态 / 产出链接），不给 M3 自由发挥空间。
- 伊森：WorkBuddy skill 同封装，权限可放宽到编辑描述与评论，适合录入 / 整理 / 预审。
- 徐总：任意入口口述，由在场智能体代写；或直接看面板人工推进。

所有智能体通过 `taskctl` 走同一个本地 API，不依赖飞书互 @、不依赖实时会议，天然规避此前连接故障（代理、事件抢占、假 connected）。

## 8. 手机端展示

| 方案 | 实时性 | 成本 | 适用 |
|---|---|---|---|
| A. 工作台「协作」页 | 静态（每 3 小时编译快照） | 零成本，复用现有管线 | 起步阶段 |
| B. 局域网直连 Taskboard UI | 实时（同 Wi-Fi） | 零成本 | 在家 / 办公室 |
| C. Taskboard 云模式（Cloudflare D1） | 实时跨网 | 需 Cloudflare 部署 | 长期、出门也要看 |

推荐顺序：先 A + B，稳定后再评估 C。

边界：任务层不并入 Supabase。Supabase 继续承担知识学习状态（方向 / 养料 / 专题），Taskboard 承担智能体任务接力，职责分开，工作台导航区分。

## 9. 与现有机制的关系

- 飞书多智能体会议流程（Obsidian 已有笔记）：保留，用于"需要多方评审"的同步讨论。
- 智能体协作状态层：用于"可拆解任务"的异步接力。两者互补：会议定方向，面板跑任务。
- 飞书连接基线与故障域（Obsidian 已有笔记）：连接验收标准继续适用；Taskboard 只依赖本地 HTTP / CLI，不依赖飞书连接，天然更稳。
- 工作台状态层（Supabase）：知识学习状态与任务状态分离，互不阻塞。
