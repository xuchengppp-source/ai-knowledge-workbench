# 给智能体：任务面板（Taskboard）操作手册

> 这是给接入任务面板的智能体（克里斯 / 伊森 / 奥利弗 / 卢卡斯 / Codex）的使用说明。请通读一遍，以后收到"建卡""登记任务""等审核"这类话，就知道该做什么了。

## 〇、总原则：Obsidian 是内容层，任务面板是状态层

先记住这条，所有动作都不跑偏：

```text
Obsidian  = 内容层：操作手册、共享问答、例会规则、机制说明的唯一真相层
任务面板  = 状态层：只显示"这件事做到哪一步了"（todo / in_progress / in_review / done）和入口在哪
```

三条铁律：

1. **内容不进面板**：卡片里永远不复制操作手册或规则正文，只写指向 Obsidian 的路径。卡片描述变长、开始塞内容，就是跑偏的信号。
2. **面板不改规则**：任何规则变更只改 Obsidian 文档本体，再在对应长期卡 `comment` 补一条记录（改了哪 / 影响谁 / 怎么验证），卡片不承载新内容。
3. **接任务先看入口**：动手前先 `list` 面板 + 读 Obsidian 操作手册；不看就动手，记一次违规。

一句话定位：**想知道"该怎么做" → 去 Obsidian 看手册；想知道"现在做到哪了" → 来面板看状态。**

## 一、你是谁，你多了什么能力

你是接入智能体任务面板的智能体之一。以前你做完一件事，大家不知道你做到了哪一步；现在有一块公共面板，你做完一件事就在面板上登记一笔：做了什么、产出在哪、下一步等谁。其他智能体看到面板状态，就知道该接哪一步，不用再挨个问。

### 两个协作角色：知识录入员 vs 知识管理员

知识流水线的入库协作分成两个层级。**所有智能体默认是"知识录入员"**；只有被徐总指定为"知识管理员"的智能体，才负责把资料完整收口。

| 角色 | 谁 | 职责 |
|---|---|---|
| **知识录入员**（默认角色） | 克里斯 / 伊森 / 卢卡斯 / 奥利弗，以及收到资料的任何智能体 | 收到资料 → 第一时间存入 `原始资料/待整理｜日期｜来源｜标题.md` → 在任务面板建卡登记。只做录入与登记，不做蒸馏、不动索引、不改专题。 |
| **知识管理员**（收口人） | 当前默认 **Codex**；徐总可临时指定 WorkBuddy / 千问办公等担任 | 负责把原始资料完整收口：蒸馏正式页 → 挂专题入口 → 更新知识库索引 → 补双向链接 → 原始资料改"已整理" → 断链校验。六步全部完成，才置 `in_review` 等徐总确认，确认后 `done`。 |

> **知识管理员的完成标准（六步收口）**：① 蒸馏正式页已建；② 专题入口已挂载；③ 知识库索引已更新；④ 双向链接已补；⑤ 原始资料已改名"已整理"并注明整理结果；⑥ 断链校验通过。六步缺一不可，全部完成才叫"完成"。

| 智能体 | 角色 | 在面板上负责的事 |
|---|---|---|
| 克里斯 | 知识录入员 | 微信 / 飞书侧搬运，收到资料先存原始资料，再建卡登记 |
| 伊森（WorkBuddy） | 知识录入员 | 收到资料先存原始资料，再建卡登记 |
| 卢卡斯（QoderWork） | 知识录入员 | 收到任务时用面板登记进度，资料先入原始资料 |
| 奥利弗（QoderWork / 千问办公） | 知识录入员 | 收到任务时用面板登记进度，资料先入原始资料 |
| Codex | 知识管理员（当前默认） | 蒸馏、索引、链接、收口、审核，六步完成置 `in_review` 等徐总确认 |

**何时升级为知识管理员**：徐总说"这次由你来收口 / 你来当知识管理员 / 你来蒸馏"时，该智能体才按知识管理员标准执行六步收口；否则一律只做录入。

## 二、职责边界（重要）

每个智能体在面板上只做自己角色内的事：

1. 完成内容整理 / 入库后，在面板上建卡登记。
2. 按审核结果改状态、加评论。
3. 按返工要求更新内容后重新登记。

不做的事：不做自己角色之外的深度梳理、不做审核（审核统一是 Codex）、不自由发挥、不动其他智能体正在处理的任务。

## 三、面板的基础信息

- 面板地址：`http://127.0.0.1:47823`（本机，只有这台 Mac 上能用）
- 协作项目：`knowledge-pipeline`（知识流水线协作）
- 任务状态：`todo` 待办 → `in_progress` 进行中 → `in_review` 待审核 → `done` 完成；`blocked` 卡住；`canceled` 取消
- 审核人：Codex。建卡时默认就是"待 Codex 审核"

### 状态判定三步问（所有卡通用，先想清楚再填状态）

**状态不看任务类型，只看"这一步活现在停在谁手里"**。任何一张卡在任何时刻都能唯一对上一个状态：

1. 内容已经完整、不再改动了吗？→ 是 → `in_review`（内容冻结，等审核人拍板）
2. 现在有人在动手做吗？→ 有 → `in_progress`（干活的在动，没干完）
3. 都不满足，只是登记好了、等下一步开始 → `todo`
4. 审核通过 → `done`

对应到两类常见任务：

| 场景 | 建卡状态 | 含义 | 下一步谁动 |
|---|---|---|---|
| 资料录入（原文已存原始资料区） | `todo` | 录入员干完了，等知识管理员接手整理 | CodeX 开始蒸馏 |
| 问题专题库（只建了标题 / 骨架） | `todo` | 骨架搭完，等 CodeX 整合 | CodeX 整合蒸馏 |
| CodeX 开始蒸馏 / 整合 / 六步收口 | `in_progress` | CodeX 正在干活，没干完 | CodeX 自己 |
| 六步收口完成、内容冻结 | `in_review` | 内容不动了，等审核 | 审核人（默认 CodeX 初审 / 徐总终审） |
| 审核通过 | `done` | 已确认 | — |

三个容易混的点：

- **CodeX 参与 ≠ 审核**：CodeX 整合 / 蒸馏阶段是 `in_progress`（他在干活），整合完成才 `in_review`（他只看不改）。
- **`todo` 不是"没人管"**：它表示"上一步已完成、下一步还没开始"。录入员整理完原文再建卡恒为 `todo`（等知识管理员接手），不是等自己开始。
- **录入员干活时**：录入动作本身长、跨会话时才临时挂 `in_progress`，干完立刻回 `todo` 再登记。

## 五、你只需要记住一个脚本、五个动作

所有操作都用同一个脚本，参数照着填就行，不用记复杂命令：

```bash
TASKCARD_AGENT_ID=oliver TASKCARD_AGENT_NAME="Oliver（千问办公）" bash /Users/xucheng/Documents/Codex项目/dashi-taskboard/scripts/task-card.sh <动作> <参数>
```

五个动作：

| 动作 | 什么时候用 | 参数 |
|---|---|---|
| `list` | 动手前先看面板上已有什么任务 | 无 |
| `create` | 内容整理入库后，登记等审核 | 主题、Obsidian 路径、来源 |
| `create-todo` | 想法 / 待办，先登记不急着入库 | 标题、来源 |
| `status` | 收到审核结果 / 返工要求后改状态（状态变了标题也要同步改） | 任务 ID、状态、新标题（可选） |
| `comment` | 补充说明（产出说明、返工完成说明） | 任务 ID、说明文字 |

### 建卡必须选类型（卡片区分）

每张卡都要有类型标签，方便一眼区分和筛选：

| 类型 | 什么时候用 | 怎么建 |
|---|---|---|
| `待办` | 想法 / 还没开始执行的任务 | `create-todo`（默认） |
| `资料录入` | 内容还没入库，先登记占位 | `create-todo --type 资料录入` |
| `知识专题` | 已整理入库，等审核 | `create`（默认） |

脚本会自动带上 `类型:<类型>` 标签；拿不准就按最接近的选。

### 建卡属性 Checklist（每张卡都要过一遍）

| 属性 | 要求 | 谁负责 |
|---|---|---|
| 状态 | 必填：`create` → `in_review`，`create-todo` → `todo` | 脚本自动 |
| 优先级 | 必填：`urgent` 今天不干有损失 / `high` 本周要交付 / `medium` 正常 / `low` 有空再做 | 建卡人 |
| 类型标签 | 必填：`类型:待办` / `类型:资料录入` / `类型:知识专题` | 脚本自动 |
| 主题标签 | ≥1 个，从词表选（`政务` `工作台` `Supabase` `体验测试` `任务面板` …） | 建卡人 |
| 来源标签 | 知识类可选：`来源:豆包` / `来源:ChatGPT` / `来源:抖音` / `来源:微信` / `来源:Claude`，标注知识从哪来 | 建卡人 |
| 工作流 | 必填：本项目统一 `issue-delivery` | 脚本自动 |
| 负责人 | 必填：按你声明的身份自动归属 | 脚本自动 |
| 开发上下文 | 开发 / 实施类必填：`--worktree-path <代码项目绝对路径>` + `--worktree-branch <分支>`；纯知识类（Obsidian 产出）不强制 | 建卡人 |
| 描述 | 必填结构化：背景 / 状态 / 来源 / 产出物 / 验收点 | 建卡人 |
| 截止日期 | 有明确时间节点时填 `--due-date YYYY-MM-DD` | 建卡人 |
| 重复周期 | 周期任务填 `--recurrence-interval N` + `--recurrence-unit day\|week\|month\|year` | 建卡人 |
| 关联 | 有拆解 / 依赖 / 相关时必建，见下 | 建卡人 |

关联怎么填（让面板上的依赖 / 子议题 / 相关视图反映真实关系）：

- 一件事拆多张卡：先建总览卡，子卡建卡时 `--parent <总览卡ID>`。
- A 要等 B 做完才能做：A 建卡时 `--blocked-by <B 的ID>`（B 会显示「阻塞了 A」）。
- 只是相关、不互相等：`--related <相关卡ID>`。

标签分层：`类型:知识专题` 是统一类型，不细分到豆包 / ChatGPT；想表达来源就用独立的 `来源:xxx` 标签；主题标签表达「哪方面的专题」（政务 / 企业AI / AI交付…）。流程标签自动清理：置 `done` 或离开 `in_review` 时脚本自动去掉「审核」；「待办」不作为标签，由状态 `todo` 表达。

完整示例（实施类待办，带上下文 / 日期 / 关联）：

```bash
TASKCARD_AGENT_ID=chris TASKCARD_AGENT_NAME="克里斯" bash /Users/xucheng/Documents/Codex项目/dashi-taskboard/scripts/task-card.sh create-todo "工作台前端接入互动状态（supabase-js）" "原型验收后实施" --worktree-path "/Users/xucheng/Documents/Codex项目/AI知识学习工作台" --worktree-branch main --due-date 2026-08-20 --parent KNOWLEDGEPIP-19 --blocked-by KNOWLEDGEPIP-14
```

## 六、看板会自动感知 Obsidian 变动（新增）

面板新增了自动感知能力，你不用时刻盯着面板：

1. 你入库的 Obsidian 笔记只要被更新，看板会自动在对应任务卡上留一条「Obsidian 笔记已更新」评论；如果这张卡已经是"完成"，会自动打回"待审核"，提醒内容变了需要重新看。
2. 建卡时务必把 Obsidian 路径写清楚（`create` 的第二个参数就是路径）。路径写对了，自动感知才认得出这张卡关联的是哪篇笔记。
3. 以后如果开了飞书通知，面板有变动会直接叫你；没开通知时，接新任务前先 `list` 看一眼面板仍是好习惯。

## 七、五个动作的详细用法

### 动作 1：list（查看现有任务）

任何建卡之前，先看一眼面板上有没有同样的任务，避免重复建卡。

```bash
TASKCARD_AGENT_ID=oliver TASKCARD_AGENT_NAME="Oliver（千问办公）" bash /Users/xucheng/Documents/Codex项目/dashi-taskboard/scripts/task-card.sh list
```

会输出一堆 JSON。只需要看两点：`identifier`（任务编号，如 `KNOWLEDGEPIP-1`）和 `title`（任务标题）。如果已经有相同主题的任务，就不要重复建，直接在这个任务上加评论说明。

### 动作 2：create（入库待审核卡，默认等 Codex 审核）

内容整理进 Obsidian 之后，用它登记。

```bash
TASKCARD_AGENT_ID=oliver TASKCARD_AGENT_NAME="Oliver（千问办公）" bash /Users/xucheng/Documents/Codex项目/dashi-taskboard/scripts/task-card.sh create "政务AI Agent工程化与上海6598万招标研究" "/Users/xucheng/Documents/c 徐的知识库/企业AI与智能体商业化/政务AI Agent工程化与上海6598万招标研究.md" "抖音豆包文案+视频转录+拆解对话"
```

三个参数：

1. `"政务AI Agent工程化与上海6598万招标研究"`：主题，一句话，不要加"审核"两个字，脚本会自动加
2. `"/Users/.../xxx.md"`：入库的 Obsidian 笔记完整路径，必须写全，含 `.md`
3. `"抖音豆包文案+..."`：内容来源，没有就写"未注明来源"

脚本会自动生成标题「审核{主题}（已入库待审核）」，状态自动设为 `in_review`，描述自动写好产出物、来源，标签自动带上 `obsidian:` 关联路径，建卡后自动留一条「建卡说明」评论。不需要手动设置状态。

建完后，会返回一个任务编号（`identifier`，如 `KNOWLEDGEPIP-1`），记下它，后面改状态、加评论都要用它。

### 动作 3：create-todo（想法 / 待办卡，先登记）

还没入库、只是先记一笔的时候用。比如测试、调研、想法，先登记不急着做。

```bash
TASKCARD_AGENT_ID=oliver TASKCARD_AGENT_NAME="Oliver（千问办公）" bash /Users/xucheng/Documents/Codex项目/dashi-taskboard/scripts/task-card.sh create-todo "美团小团 AI 体验测试与工程化分析" "今早实测，体验问题疑与工程化相关"
```

两个参数：

1. `"美团小团 AI 体验测试与工程化分析"`：标题，一句话说清要做什么
2. `"今早实测，体验问题疑与工程化相关"`：来源 / 背景，没有就写"未注明来源"

脚本会自动生成标题「{标题}（待办）」、状态 `todo`、标签 `待办`，描述写清背景 / 状态 / 来源，建卡后自动留「建卡说明」评论。

开发 / 实施类待办要绑定代码项目与分支（开发上下文），面板卡片上会显示绑定位置；纯知识类卡（Obsidian 产出）不用绑：

```bash
TASKCARD_AGENT_ID=chris TASKCARD_AGENT_NAME="克里斯" bash /Users/xucheng/Documents/Codex项目/dashi-taskboard/scripts/task-card.sh create-todo "工作台前端接入互动状态（supabase-js）" "原型验收后实施" --worktree-path "/Users/xucheng/Documents/Codex项目/AI知识学习工作台" --worktree-branch main
```

### 动作 4：status（改状态）

收到审核结果后使用。比如 Codex 审核通过，他会把任务置为 `done`；如果他发现问题打回，任务会变成 `in_progress`，返工完成后再置回 `in_review`。

```bash
TASKCARD_AGENT_ID=oliver TASKCARD_AGENT_NAME="Oliver（千问办公）" bash /Users/xucheng/Documents/Codex项目/dashi-taskboard/scripts/task-card.sh status KNOWLEDGEPIP-1 in_review
```

参数：

1. `KNOWLEDGEPIP-1`：任务编号（建卡时返回的那个）
2. `in_review`：状态，只能填 `todo` / `in_progress` / `in_review` / `blocked` / `done` / `canceled`

**状态和标题必须一起改，不能只移动状态。** 置 `done` 时把标题里的「审核整理：」「（已入库待审核）」等流程词去掉，只留干净的主题名；置 `in_progress` / `todo` 时去掉残留的「（待办）」。第三个参数传新标题即可：

```bash
TASKCARD_AGENT_ID=oliver TASKCARD_AGENT_NAME="Oliver（千问办公）" bash /Users/xucheng/Documents/Codex项目/dashi-taskboard/scripts/task-card.sh status KNOWLEDGEPIP-1 done "政务AI Agent工程化与上海6598万招标研究"
```

### 动作 5：comment（加评论）

补充说明时使用。比如返工完成、补充产出说明。

```bash
TASKCARD_AGENT_ID=oliver TASKCARD_AGENT_NAME="Oliver（千问办公）" bash /Users/xucheng/Documents/Codex项目/dashi-taskboard/scripts/task-card.sh comment KNOWLEDGEPIP-1 "返工完成，已按意见补充工程能力域对比"
```

## 八、完整流程：从收到任务到建卡

用户对你说："把政务招标整理入库后，建卡等 Codex 审核。"

你要做的：

1. 用你已有的能力，把内容整理进 Obsidian（入库）
2. 先 `list`，确认面板上没有同样的任务
3. 执行 `create`，填主题、Obsidian 路径、来源
4. 记下返回的任务编号
5. 回复用户："已完成入库，已建卡「KNOWLEDGEPIP-1」等待 Codex 审核"

## 八点五、资料入库流转卡（原文 → 蒸馏）

> **核心规则**：外部资料（转发长文、ChatGPT 对话、抖音/豆包文案、视频转录等）**不能直接进问题专题库**。先判断归属，再建卡，卡片必须体现"原文先放哪 → 整理后放哪"两个路径。

**默认动作（知识录入员）**：

```text
收到徐总转发内容、要求录入/整理
  → 原文存入 原始资料/待整理｜日期｜来源｜标题.md
  → 任务面板 create-todo 建卡（写清：原文存放路径 + 蒸馏后目标路径 + 来源）
  → 状态 todo，等知识管理员接手
```

**先判定类型再动作**：

```text
收到内容
├─ 外部资料（无明确落点）→ 存原始资料/待整理 → create-todo 建卡
├─ 问题（要回答/判断）→ 走问题专题库，卡片填问题专题库路径
└─ 成型判断 + 徐总明确指定落点（"直接进 XX 专题"）→ 直接沉淀正式页 + 面板登记，不另建原始资料
```

**多 bot 去重**：先 `list` 再建卡；同主题已有卡就不重复建。徐总指定了谁就谁录入；未指定时谁先建卡谁是第一录入责任人，其余 bot 只 `comment` "我也收到了"，引用原文路径，不复制原文、不建新卡。

**自己生成的产物（会议纪要 / 复盘 / 修复记录 / 报告）不走录入两步**，直接按 D_输出成果 / Codex工作区 / 对应专题落位，产出后面板登记即可。

**原始资料 frontmatter 模板（录入时就要写）**：

```yaml
---
title: <标题>
type: 原始资料
level: 一级原文
status: 待整理
created: <YYYY-MM-DD>
source: <平台 / 账号 / 链接>
captured_by: <WorkBuddy / 克里斯 / 豆包 / 其他>
suggested_topic: 待判断
tags:
  - 原始资料
  - 待整理
---
```

整理完成时统一改 `status: 待整理 → 已整理`、移除 `待整理` 标签、`suggested_topic` 改实际归属专题。

> 边界疑问与回答见 Obsidian「Codex工作区/智能体例会问题登记（共享问答）」。

**状态流转**：

```text
todo（原文已存入原始资料区，等知识管理员接手）
  → in_progress（知识管理员开始蒸馏，六步还没全部完成）
  → in_review（蒸馏 + 索引 + 链接 + 原始资料改状态，六步全部完成，等徐总确认）
  → done（徐总确认完成）
```

**状态含义速记**：

```text
in_progress = 六步有没做完的，正在精进中
in_review   = 六步全部完成，就是可以确定的状态，等徐总拍板
done        = 徐总已确认
```

> 通用判定：任何任务（不止资料入库）都按第三节「状态判定三步问」定状态。

**知识管理员六步收口**（被指定为知识管理员才执行）：

1. 蒸馏（先判融合还是新建）：优先把原文融合进已有的相关正式页、专题入口或方法论页；只有形成新的方法、框架、案例样本且没有合适落点时，才新建正式页。无论融合还是新建，都注明来源和"整理结果"回链。
2. 挂专题入口，在对应专题入口页加一条。
3. 更新 `知识库索引.md` 对应分区（路径 / 类型 / 内容方向 / 核心价值 / 关联页 / tags）。
4. 补双向链接，让蒸馏页与相关正式页互相可跳转。
5. 原始资料改名 `已整理｜日期｜来源｜标题.md`，frontmatter `status: 待整理 → 已整理`，勾选待整理项并写明 `整理结果：[[正式专题/蒸馏页]]`。
6. 断链校验，确认相关页无断链。

六步全部完成 → `status in_review` → 等徐总确认 → 确认后 `status done`。中途有任何一步没做完，任务停在 `in_progress`，不得置 `in_review`。

> **融合优先原则**：蒸馏不是"每篇原文都新建一页"。先扫知识库，能融进现有页就融（补节、补案例、补术语），只有真没有落点才新建。面板卡片上要写清"融合到哪页 / 或新建哪页"。

## 九、返工流程

1. Codex 审核发现问题，会把任务打回 `in_progress`，评论里写明返工要求
2. 打开任务评论，看返工要求（用 `list` 或看面板）
3. 按要求修改 Obsidian 笔记
4. 改完执行 `comment` 说明改了什么
5. 再执行 `status <任务ID> in_review`，重新等待审核

## 十、注意事项（违反会出错）

1. **先 `list` 再 `create`**，绝不重复建卡
2. **每次操作都要带自己的身份**（`TASKCARD_AGENT_ID` + `TASKCARD_AGENT_NAME`），不带会被记成 Codex
3. 状态只能填那 6 个词，不要发明新状态
4. **不要动别人的任务**，除非评论里明确是返工要求
5. Obsidian 路径必须写全（含 `.md`），不要写简称
6. 只做自己角色内的事，不做审核、不做自由发挥
7. 拿不准时，先 `list` 看面板，再问徐总，不要猜
8. **默认只做知识录入员**：收到资料 → 存原始资料 → 建卡，即可交差。蒸馏 / 索引 / 链接 / 改状态是知识管理员的事，不被指定就不要越界
9. **知识管理员完成标准 = 六步收口**：蒸馏 + 挂入口 + 索引 + 链接 + 原文改已整理 + 断链校验，缺一步都不算完成，任务停在 `in_progress`，不得置 `in_review`
10. **最终确认权在徐总**：知识管理员只置 `in_review`，由徐总确认后才 `done`；未经确认不得自行置 `done`
11. **蒸馏融合优先**：能融合进现有笔记的必须融合，不要每篇都新建页；新建只在没有合适落点时发生
12. **先判定类型**：收到内容先判断"外部资料 / 问题 / 成型判断+指定落点"，再决定走原始资料、问题专题库还是直接沉淀
13. **多 bot 去重**：群内同份资料只建一张卡、只存一份原文；先 list，指定了谁就谁录入，否则先建卡者是第一责任人
14. **自己生成的产物不走录入两步**：纪要/复盘/报告直接落位，面板登记即可
15. **原始资料录入时就带 frontmatter**：`status: 待整理`、来源、标签，避免后补

## 十一、做完一件事，自检三个问题

1. 我带上自己的身份了吗（不是 Codex）？
2. 我入库的 Obsidian 路径写全了吗？面板上有没有重复的任务？
3. 我回复用户时，说明清楚任务编号和状态了吗？
4. 我是知识录入员还是知识管理员？录入员是否已把原文存进原始资料并建卡？管理员是否六步收口全部做完？

都确认了，这件事就做完了。
